# Вдвоём

Интерфейс рассчитан прежде всего на телефон: крупные карточки встреч, неделя с раскрытием полного месяца, быстрые действия на главном экране и постоянная кнопка «+» в нижней навигации. Основной текст — 15–16 px, поля — 16 px, кнопки — от 44 px. На компьютере показывается тот же интерфейс в узкой рамке.

Выбранные варианты переносятся в план через закреплённую кнопку. В конструкторе свиданий страницы переключаются горизонтально, а сохранение и отправка остаются внизу экрана. Поиск атмосфер помогает выбрать сценарий без просмотра всех карточек. Мобильные проверки охватывают ширины 320, 360, 390 и 430 px.

Адаптивный сайт для пары: общий календарь с двумя видами учёта — свидания и секс. Есть выбор формата отношений, независимые планы и факты, каталог из 96 вариантов в 24 подкатегориях, собственные названия поз, статистика регулярности, сценарии свиданий, история, личные заметки и оценки. Серверная версия поддерживает установку как веб-приложения и Web Push. Общие принципы вдохновлены TimeTree, Cupla, Intimassy и xTracker; интерфейс и реализация собственные.

## Локальный запуск

Установка на iPhone, различия между приглашением и прямым планом, приватность пушей и требования публикации: [мобильная версия и уведомления](docs/MOBILE_AND_NOTIFICATIONS.md).

Требуется **Node.js 24+**, npm и доступ к npm registry. Внешняя база данных и ключи API не нужны.

```bash
cd /workspace/Callendar
npm ci
npm run dev
```

Приложение слушает порт **3000** на всех интерфейсах. Один процесс обслуживает React/Vite, API и SSE. Для готовой сборки:

```bash
npm run build
npm start
```

## Как пользоваться

1. Откройте сайт. Демо показывает примеры; изменения в демо находятся только в памяти вкладки.
2. Нажмите **«Создать пару»**, введите имя, выберите **«Встречаемся»** или **«Мы пара / в браке»** и создайте чистый календарь. В первом формате основной акцент — свидания, во втором — близость. Название отношений необязательно; права участников одинаковы.
3. Отправьте ссылку-приглашение партнёру. Он открывает её **в своём браузере** и вводит имя. Ссылка однократная, действует 7 дней; новое приглашение отменяет предыдущее.
4. Добавляйте и меняйте свидания и встречи близости. Фильтры **«Все встречи / Свидания / Секс»** разделяют учёт. Общий календарь обновляется у обоих через SSE. При потере связи подключение восстанавливается автоматически.
5. В разделе **«18+»** можно запланировать близость или **«Добавить факт»**: любой участник добавляет состоявшуюся встречу, сразу видимую обоим, без второго подтверждения. Время факта необязательно. Метки и общие пожелания видны обоим.
6. В карточке свидания нажмите **«Запланировать секс отдельно»**, чтобы создать связанную запись. Завершение свидания не завершает интимную встречу. При удалении свидания связанная близость сохраняется, её связь снимается.
7. Откройте встречу, чтобы оставить **личную заметку**, а после состоявшейся близости — необязательную личную оценку от 1 до 5. Эти поля доступны через API только с сессией автора и не входят в общие ответы или события синхронизации.
8. Нажмите **«Встреча состоялась»**, чтобы сохранить момент в истории. Статистика интимной жизни считает только состоявшиеся встречи за последние 28 дней; будущие планы показаны отдельно.
9. **«Изменить формат»** меняет общий акцент без потери записей. По желанию задайте общую частоту близости; по умолчанию цели нет. Изменения настроек также синхронизируются и защищены версией.

Встречи хранят локальные дату и время, без автоматической конвертации старых записей. «Сегодня» и период статистики определяются в зоне `Asia/Almaty` (UTC+5); настройка зоны пары запланирована отдельно. При одновременном редактировании версия встречи предотвращает потерю правки партнёра.

Обновление БД добавляет только таблицы настроек и приватных оценок; существующие события, сессии и заметки сохраняются. Старые записи без типа отображаются как свидания, прежнее текстовое продолжение не становится фактом близости автоматически.

## Идеи для свиданий: модуль из архива

Раздел полностью заменён конструктором из `Date_Module_Codex_Integration`: перенесены все 10 атмосфер, тексты, места, занятия и фон ночного Алматы. Вместо прежних шести карточек здесь **«Атмосферы / Созданные / Входящие»**. Каждая атмосфера имеет собственное оформление и сохраняется на всех страницах сценария.

1. Выберите атмосферу и режим: партнёр выбирает детали или получает готовый план/сюрприз.
2. Настройте страницы: текст, кнопки, один или несколько вариантов, ветки, дату и финальное принятие. Можно добавлять страницы после этапа или внутри конкретной ветки. Общий переход объединяет ветки; множественный выбор использует один следующий этап.
3. Сохраните черновик либо отправьте приглашение. Черновик доступен автору; для отправки нужен подключённый второй участник.
4. Партнёр открывает входящее приглашение и выбирает детали. Прогресс сохраняется. Возврат и изменение выбора удаляют ответы прежней ветки.
5. Принятие сохраняет полный ответ и создаёт **одно запланированное свидание**. Ответ доступен обоим в карточке; оттуда можно перейти к событию календаря. Повтор отправки не создаёт дубликат.

Опубликованный сценарий хранится отдельным снимком. Если автор редактирует и публикует новую версию, уже начатый путь партнёра продолжает прежнюю. Сервер проверяет варианты, дату, полный путь, права пары, циклы и переходы. Максимум — 100 страниц, 20 вариантов на странице; запросы модуля ограничены 512 КиБ.

В статическом демо можно переключать **«Я — первый партнёр / Я — второй партнёр»**, чтобы пройти весь сценарий самостоятельно. Черновики и ответы сохраняются при переходе между разделами в текущей вкладке; перезагрузка сбрасывает демо. В серверной версии роли определяет сессия, записи сохраняются в SQLite, обновления приходят обоим через SSE.

В календаре **синие карточки с сердцем — свидания**, **розовые с отдельным значком — секс**. Часы обозначают план, галочка — состоявшуюся встречу. Есть легенда и фильтры; форматы свиданий не меняют цвет типа учёта.

Доступ к приглашению требует действующую сессию участника той же пары; сама ссылка с ID доступа не даёт. Отдельный PIN приглашения, аккаунты для повторного входа и расширенные настройки времени пока не добавлены. Целевая архитектура описана в [плане интеграции](docs/DATE_MODULE_INTEGRATION_PLAN.md).

## Проверки

```bash
npm test
npm run build
CHROMIUM_PATH=/usr/bin/chromium npm run test:e2e
```

Если системного Chromium нет, установите браузер Playwright через `npx playwright install chromium` и выполните `npm run test:e2e`. В облачной среде Chromium уже доступен.

Серверные проверки покрывают подключение партнёра, настройки отношений, оба типа встреч, SSE, изоляцию заметок и оценок, связи событий, версии, проверку ввода, обновление старой БД и сохранение после перезапуска. Браузерные проверки проходят сценарии двух партнёров на компьютере и телефоне. Они запускают отдельный сервер на порту 3100 с временной БД и не изменяют ваши встречи. Скриншоты находятся в игнорируемой папке `test-results/`; отдельные результаты статического просмотра — в `preview-test-results/`.

## Данные и размещение

### Cloudflare Free — без карты и покупки домена

Подключите репозиторий как **Worker**. Сборка: `npm run build`, публикация: `npm run deploy:cloudflare`. Интерфейс и API публикуются вместе; постоянная SQLite-база Durable Object создаётся автоматически, D1 вручную настраивать не требуется. [Пошаговая инструкция Cloudflare](docs/CLOUDFLARE.md).

На Free синхронизация открытого приложения выполняется каждые 15 секунд и при возвращении на страницу. Подписки календаря и Web Push работают через серверный API. Бесплатный тариф ограничен квотами Cloudflare; платный план конфигурацией не запрашивается.

### Серверная версия без подписки GitHub

GitHub Free подходит для хранения исходников. Для совместной работы нужен отдельный сервер с постоянным диском. Подготовлен запуск через Docker Compose: приложение, сохранение SQLite и автоматический HTTPS. Можно использовать подходящий бесплатный сервер; тариф и ограничения определяет провайдер. Покупать домен необязательно.

[Инструкция запуска серверной версии](docs/SERVER_DEPLOYMENT.md). Размещение требует сервера или аккаунта хостинга; коммит в GitHub не запускает API.

### Развёртывание на Render

В корне есть `render.yaml`: Node.js 24, сборка, запуск, проверка состояния и постоянный диск на 1 ГБ. **Blueprint выбирает платный тариф Starter и диск; перед созданием ознакомьтесь с актуальной стоимостью Render.** Бесплатный Web Service без постоянного диска не подходит для хранения вашего календаря: данные могут теряться при перезапусках.

1. Создайте аккаунт на [Render](https://render.com/) и подключите GitHub.
2. Выберите **New → Blueprint** и репозиторий `viktor945/Callendar`, ветку `main`.
3. Проверьте предложенные услуги и стоимость, затем запустите развёртывание.
4. После успешной сборки Render выдаст HTTPS-адрес сервиса. Сервер использует `RENDER_EXTERNAL_URL`, чтобы правильно проверять Origin и выставлять Secure-cookie. Для собственного домена установите `PUBLIC_ORIGIN`.
5. Откройте адрес, создайте пару и отправьте приглашение партнёру. После обновления сервиса календарь останется на подключённом диске.

Автоматическое развёртывание в blueprint отключено: новые изменения запускаются вручную из панели. Пароли, приглашения, SQLite и `.env` не отправляются в GitHub.

### Переменные и хранение

SQLite по умолчанию находится в `.data/calendar.sqlite`; папка исключена из Git. Не удаляйте её при обновлении. Для размещения нужен постоянно работающий **Node-сервер с постоянным диском** — статического хостинга недостаточно.

| Переменная | Назначение |
| --- | --- |
| `PORT` | Порт сервера, по умолчанию `3000` |
| `DATABASE_PATH` | Путь к SQLite на постоянном диске |
| `PUBLIC_ORIGIN` | Канонический адрес сайта, например `https://calendar.example.com`, без завершающего `/` |

На публичном сервере настройте HTTPS и `PUBLIC_ORIGIN`; это включает Secure-cookie и проверку источника изменяющих запросов. Прокси должен передавать SSE без буферизации и поддерживать долгие соединения. Для резервной копии остановите сервер и скопируйте папку БД целиком, включая WAL-файлы, если они присутствуют.

Это первая версия с входом по однократному приглашению и сессиями браузера. Сессия действует 180 дней; восстановления после очистки cookie, входа на новом устройстве и смены партнёра пока нет. Не очищайте cookie рабочего календаря. Приглашение даёт доступ к общим данным, поэтому передавайте его лично. Личные заметки разделены на уровне API, но **не зашифрованы от администратора сервера**. Полноценные аккаунты и восстановление доступа нужны перед использованием как постоянного публичного сервиса.

Web Push для приглашений, ответов и изменений общих планов реализован в серверной версии по HTTPS. Напоминания по времени, импорт внешних календарей, повторяющиеся встречи и интеграции с упомянутыми приложениями пока не входят. Внешние календари и данные других приложений не запрашиваются.

## Структура

- `src/` — React + TypeScript, адаптивный интерфейс и подключение SSE.
- `server/index.mjs` — HTTP API, сессии, приглашения и встроенная SQLite.
- `server/dates.mjs` — черновики, версии, прогресс и атомарное сохранение ответа/свидания.
- `server/push.mjs` — подписки устройств, постоянные VAPID-ключи и нейтральные уведомления нужному партнёру.
- `public/manifest.webmanifest`, `public/sw.js`, `public/icons/` — установка веб-приложения и обработка фоновых пушей.
- `src/features/intimacy/` — каталог настроений, подкатегории, наборы и статистика.
- `src/features/dates/` — перенесённые шаблоны, темы, редактор, проигрыватель и общий движок проверки сценариев.
- `server/dates.test.mjs` — ветки, приватность, версии и повторные ответы.
- `server/index.test.mjs` — серверные интеграционные проверки.
- `tests/` — браузерные сценарии Playwright и сервер с временной БД.

Используйте существующий checkout: каждая облачная задача уже изолирована, дополнительный Git worktree не нужен.
